## Shared authoritative configuration

Add portable `src/rendering/GraphicsSettings.h/.cpp`, independent of Vulkan headers and JNI. Keep platform storage adapters thin. Proposed types:

- `GraphicsSettings`: schema version, fixed scale percent, water mode, fire detail, menu/preview cap. Preserve existing scale bounds 50–100. Add later admitted controls to this single type.
- `GraphicsCapabilities`: actually compiled optical profile, available water/fire modes, supported backend, sizing limits, optional timing/memory availability, reason codes. Optical profile is an effective capability in the initial slice rather than a false runtime choice.
- `GraphicsResolution`: requested settings, resolved settings, unsupported/constrained reasons, actual internal/output width/height, profile name (`Accepted 1.6.1 baseline`, supported presets, `Custom`). A preset is a deterministic value bundle; changing a member makes Custom. Never infer a preset from its name alone.
- `GraphicsEditSession`: committed, draft, pending candidate, last known usable, monotonic request serial, state (`Editing`, `Applying`, `AwaitingConfirmation`, `Committed`, `Reverting`, `Failed`). A pure transition reducer makes application/acknowledgement/recovery host-testable.
- `GraphicsAppliedSnapshot`: serial, actual resolved values/dimensions, RT backend/optical profile, apply result/reason, current scene, lifecycle generation. UI labels consume this snapshot, never requested atomics.

Suggested functions: `MigrateLegacyGraphicsSettings`, `ResolveGraphicsSettings`, `MatchGraphicsPreset`, `BeginGraphicsEdit`, `StageGraphicsEdit`, `RequestGraphicsApply`, `AcknowledgeGraphicsApply`, `ConfirmGraphicsApply`, `RequestGraphicsRevert`, `ResetGraphicsDraft`. Return structured reason enums with platform-local strings. No GPU calls or persistence inside the reducer.

Start with a platform-native named baseline: Android 75%/Mobile water/Mobile fire, Windows 100%/High water/High fire, and the actual compiled optical profile. Preserve every user's saved value, even if migration produces Custom. Useful presets can be `Baseline`, `Reduced effects` (Mobile water/fire, same saved scale), and `Custom`; list full values and label costs not yet measured. Do not call Reduced effects cheaper until measured. A High optical preset unavailable in a Mobile build must explain why. Preview animation pause and camera are session controls, not graphics preset members.

Use a coherent bounded mailbox (the established `InputMailbox` synchronization pattern or owner-thread mutex/copy) for Android graphics command publication. Do not combine newly independent configuration fields through unrelated atomics. UI and render owner must agree on serial and lifecycle generation; obsolete requests/acks cannot commit settings after resume or a later Apply.

### Transaction and persistence

1. Opening Graphics clones the committed configuration into a draft and records the return surface. Gameplay/input is paused before preview entry. Slider changes only edit the draft; Apply submits one coherent candidate. Optional live-preview debouncing still uses the same transaction and never persists unconfirmed values.
2. At the render owner boundary, wait/complete owned graphics work, reset command-buffer references/evidence when needed, resolve capabilities, and use `ResizeOutputAfterDeviceIdle` for scale. The scene's output resize already rolls back resources/descriptors on allocation failure. Keep old effective settings/dimensions until success. Apply water/fire per-frame inputs atomically after that boundary.
3. A successful GPU resource transaction enters confirmation only after an RT-produced candidate frame successfully presents. Publish actual `DispatchExtent`, swapchain extent and effective profile. A suboptimal present remains a successful present but triggers recreation and excludes steady performance comparison.
4. Confirm persists the committed settings and last known usable version. Revert/cancel/back restores the entry values through the same transaction. Reset changes only the Graphics draft to the named baseline and requires Apply/Confirm.
5. Persist a separate pending marker before potentially unusable application. If the process dies or the surface disappears during unconfirmed application, restore the last confirmed values on next startup and explain recovery. Never overwrite the retained requested candidate with a lower-quality value. Store recovered effective settings and retained requested values separately where they differ.
6. A bounded confirmation deadline (proposed 15 seconds of visible foreground time) restores the last usable configuration if unconfirmed. Background cancels/reverts or suspends the deadline explicitly; background duration must not silently confirm. Allocation failure should report failure and continue the old valid output; device loss has a distinct renderer diagnostic/recovery route.

Scale application currently terminates Android's loop on resize failure despite shared output rollback; the Phase 2 adapter must fix that. Windows Phase 1 A4 owns its efficient resize integration; Phase 2 wraps that path instead of creating another one. Do not double-recreate evidence or discard a valid old output because an optional observer reset fails.

## One active production RT preview

Use `PresentableTinyRtScene` for both content profiles. Add `RtSceneContentProfile { Showcase, GraphicsPreview }` to initialization and a small immutable `RtSceneContentDescription`/geometry recipe. Add `src/scene/GraphicsPreviewScene.h/.cpp` for authored positions, fixed camera IDs (`Overview`, `Materials`, `Glass`, `Water`, `Skeleton`, `Mirror`), deterministic scene seed and repeatable motion path. This is scene data, not shader branches by preview object.

Extract the existing quad/box/world-surface construction helper from `BuildAccelerationStructures` into a shared builder with vertex/index/surface-code outputs. A profile supplies compact alcove walls/floor, mirror, admitted material surfaces, modest closed waterfall streams/pool and a pane using existing production dielectric fixture. Reuse ordinary shader material codes and existing `RtStaticMeshSlot` registrations. Keep water dimensions and shader stream centers derived from the same authored data; current water shader helpers and transforms contain world-coordinate constants, so blindly moving the waterfall will produce mismatched interfaces. Make that existing coupling authorable through shared data before relocating it. Retain the frame/shader ABI checks.

Add portable `GraphicsPreviewSession` (owner thread) with deterministic 60 Hz local timeline, reset/freeze and motion test, producing immutable `RtSceneFrameInputs` through a renderer adapter. It does not mutate `GameSimulation`, advance combat/rewards, drain gameplay events or write saves. Set exactly one skeleton Idle/Locomotion snapshot; use `CharacterRenderSlot` and actual admitted asset/animation. Reuse `FireEmitterState` advancement/socket derivation for preview torch/lantern. A world lantern must use admitted ring/body resources and shared flame/light sockets without manufacturing a reward state in gameplay. Choose clear preview-only content transforms through the content description, not `productionRewardPropsVisible` and `glassFixtureVisible` hacks that mutually suppress chest/fixture/props.

GPU ownership recommendation: one active scene allocation set. On entry, retain the paused `GameSimulation` object/snapshot and its lifecycle/input sequence floors in CPU memory; complete graphics work and destroy the active showcase scene only, then initialize the preview profile with the same device/swapchain/backend and exact provider. On exit, complete owned preview work, release preview resources and initialize Showcase; render the unchanged simulation snapshot before resuming. UI acknowledgement is pending until successful RT presentation. This bounds peak GPU duplication. Do not call a platform full-context constructor that resets simulation/progress or retains references to destroyed buffers.

If scene reinitialization fails, return to the prior content profile/last usable settings with a bounded diagnostic; if that restoration also fails, show the native renderer error surface. Keep the last visible image/scrim while loading and expose loading/transition time. Do not render both scenes or label the old image as a successfully presented new preview. An alternative retaining both complete GPU scenes is rejected initially because it duplicates allocations on Android; reconsider only with measured budgets and a demonstrated transition need.

Minimal implementation may share asset CPU descriptions, but preview GPU content must not include the full dungeon just hidden by masks. Initial `LoadStaticHeldItemAssets` and `CharacterRenderSlot::LoadAssets` are strict all-content loaders; add narrow content/actor admission arguments so preview can exclude lich/chest/roof and unnecessary player resources without a silent missing-required-asset fallback. Reusing existing asset files does not authorize relicensing/removal of the shipped skeleton or claim its owner-tracked Hotstrike limitation is resolved.

The preview UI uses the native rendered surface plus a restrained scrim/side or bottom controls, not a screenshot widget. Keep default stable Overview, explicit camera selection, Pause/Resume preview, Reset timeline, A/B baseline/draft and motion test. Selecting a setting may offer Focus without forcing camera motion. Switching A/B resets timeline/camera and invalidates preview history/evidence; gameplay history is invalidated on scene restoration. No continuous captures/readback.

Use explicit visible menu cap (proposed 30 Hz on both platforms, shown as effective cap). Cap via interruptible owner-loop pacing outside measured GPU/record work; include paced wall time in presented-throughput measurement. Background stops preview rendering and timeline advancement. Preview pause freezes animation; keep a capped renderer active for camera/settings or render on demand only after an explicitly implemented resource-valid policy. An owner-invoked performance/motion test may use its displayed test cap; ordinary Settings never silently uncaps.

## Truthful bounded telemetry

Add `src/telemetry/GraphicsPreviewPerformance.h/.cpp`: fixed 128-row ring, scope ID/content epoch, transition flag and wall-time boundaries. A UI snapshot at 4 Hz provides smoothed numerics and unsmoothed short graph. UI polling must copy a coherent snapshot and avoid file logging. Existing evidence serials remain sole owners.

- Title exactly **Preview scene performance**; show backend, compiled optical profile, effective water/fire, internal/output dimensions and cap.
- **RT successful presents/s** counts `RtPresentationSucceeded` outcomes over wall time (include suboptimal as successfully presented but mark transitions). Explain these are successful swapchain presentations, not scanout timestamps/displayed refresh; present queue return does not prove on-screen display.
- **Loop interval** measures owner-loop wall time including cap waits; **CPU render call**/`WholeFrameCycle` and **GPU work ms** remain separate. GPU data comes only from exact completed evidence; invalid/error/unavailable explicitly shown.
- Keep transition stalls in graph with loading/apply/revert/recreation/history-warm markers; exclude them from an explicitly labelled stable-sample statistic rather than quietly discarding them. Scene/preset/timeline epochs prevent mixed A/B samples.
- **Tracked scene device-local allocations** and **tracked host-visible allocations** come from actual `ResourceInventory`; labels state overlap possible on shared memory. Add unique-allocation total only after inventory provides it. No summing the two classifications. Budget/capacity is **unavailable** until a separate `VK_EXT_memory_budget` capability/per-heap accounting slice exists. Phone RAM never becomes dedicated VRAM.
- Measure observer-on/off overhead and resource/timer allocations. Preview is illustrative, not sustained full-game FPS evidence; the separate benchmark and fixed 75% S26 target stay intact.
