# Horde 1.7 WP2 Vertical-Transform Proof Proposal

Prepared 9 October 2026. This is one proposed early runtime slice after WP0. It is a design proposal only; no code or test changes are included here. The source authority is accepted runtime baseline `1c28d0563a897dc72d410bdb2b61723e66ed92af`; the planning direction is pinned commit `d37f16381311c6e620f0c4a9d01c1cce83260dc8`.

The pinned master calls vertical movement WP2; **WP2a is its separate combat-timing package in Section 5.6**. This proposal is only a bounded vertical-transform fixture within WP2. It should answer whether meaningful supported height can pass through the current engine contracts before rope or forest expansion. It does not implement a zone loader, streamer, or camera-only height trick.

## Proof outcome

Use a compact fixture in the existing dungeon coordinate frame: preserve the current ground route, add a supported raised surface and a controlled transition between them, then exercise both directions in the existing resident scene. Keep this proof focused on the authoritative transform, support/collision, camera, body/sockets/light and event-time listener. Capture views looking up and down, including an RT contributor that is off-camera but still affects a shadow/reflection/transmission path. Do not add a second residency mode or zone-retirement implementation here.

The inherited preloaded-versus-staged comparison remains a later WP2/WP3 evidence decision using representative blockout geometry and measured residency, preparation latency, warm CPU/GPU work and RT dependencies. Make that comparison before forest scale-up, under matched conditions on the actual targets. No numeric capacity/performance budget or streaming architecture is selected by this early transform proof.

## Transform and ownership contracts

Treat player Y as the authoritative support/root elevation in world space. The current corridor's support elevation is the zero-offset reference: `kRouteFloorWorldY == -0.95f`, while `kShowcaseEyeWorldY == 0.70f` (`src/gameplay/ShowcaseRoute.h`). These are absolute world coordinates; do not move the floor to zero. Proposed `playerSupportWorldY` starts at -0.95, and `playerHeightDelta = playerSupportWorldY - kRouteFloorWorldY` starts at zero. Preserve the 1.65 m eye-above-support relationship and existing bob/retraction offsets. Local eye, body, hand and socket offsets remain authored relative to that root and are composed once. A camera pitch change, renderer-only offset, or platform-specific Y is not authoritative movement.

| Contract | Owner and proposed boundary |

Collision/support resolution returns the accepted transform; views and render adapters do not independently infer traversal height. `InputSnapshot.h` must carry a full authoritative pose only for the existing controlled/capture path when needed, not a second gameplay authority. |

Keep the current RT pipeline and successful RT-produced presentation contract. Derive any shader/ABI edits from the actual camera data path; do not duplicate a root offset in both CPU and shader code. |

## Zero-height compatibility invariants

At the existing corridor support height (`playerHeightDelta == 0`, support remains -0.95 m):

- Existing X/Z movement, yaw, walk/collision results, fixed-step tick ordering, encounter placement and progression remain unchanged.
- Camera origin, body pose, hand targets, sword/torch/lantern socket transforms, flame/light origin and event-time audio listener reproduce the current transforms. Add root Y once; preserve all existing local offsets.
- Existing corridor support and collision decisions remain the same. No new floor snapping, camera bob, slope response or transition logic alters the old route in this fixture.
- CPU-authored transform outputs are deterministic and equal to the established zero-height results. RT image comparisons are matched within the same build/device conditions; do not require byte identity across unrelated GPUs.

At a nonzero supported height, all those world-space transforms translate by the support delta while local transforms and X/Z remain stable. Lighting, body shadow/reflection participation, and listener source-relative positioning must agree with the translated world pose. Invalid, missing or stale support must not silently become a renderer-only height.

## Focused test and acceptance plan

Host tests for the proof should cover:

- A zero-height snapshot and frame-input regression for unchanged X/Z, camera, body, item sockets, held-light origin, and event listener tuple.
- A nonzero-height supported pose reaching the renderer camera, player body, both hand targets, sword/lantern sockets, physical light, and delayed event listener; verify a single root translation and stable local offsets.
- Support changes and collision across the raised fixture while preserving the legacy route; invalid support cannot silently move the camera or alter the player independently of simulation.
- RT view checks under the raised fixture, including off-camera contributors, with CPU pose/transform evidence separated from renderer outputs.

Later WP2/WP3 work must test stale readiness callbacks, failed-load rollback, submitted-resource retirement and compare preloaded with staged residency using matched measured evidence. Do not pull those mechanisms into this first fixture.

Later acceptance must use exact Android and Windows candidates on supported hardware and each supported hardware-RT backend: the `vkCmdTraceRaysKHR` pipeline and, where selected/supported, the authorized `RayQueryCompute` backend using real BLAS/TLAS-backed hardware ray queries and shared shading. Record backend identity and require genuinely RT-produced successfully presented frames; a dispatch, host test, screenshot, desktop pass or SoC claim is insufficient. Exercise supported-height movement both directions, look up/down, and shadows/reflections/transmission with relevant contributors off-camera. For this fixture, repeat reset/retry, Android pause/background/resume, portrait/both landscape rotation, surface loss/recreation and process reconstruction, plus Windows focus/resize/recovery/restart. Confirm no stale input/frame/surface generation or delayed feedback can restore an old height. Later zone callback tests add stale readiness publication rejection when that system exists. Keep backend/device evidence separate and report unavailable targets as open gates.

The later full rope traversal package may consume the proven transform/support and future readiness/rollback boundaries. It must separately add rope physics, grip/load/contact/release, safe mantle, stowed/carried equipment behavior, and climb usability. Kit production, forest assets, save UI, themed UI and combat timing remain outside this proof. No full rope, Kit, forest, save UI or combat implementation is part of this proposal.

## Proposed review gate

Accept this proof only when the old zero-height route is preserved and supported height reaches every named world-space consumer in the existing resident scene, with the intended backend producing and successfully presenting RT frames on the exact targets. If device access is unavailable, host-side implementation may continue, but hardware/backend acceptance remains open. The separate preloaded-versus-staged resource decision stays with later WP2/WP3 and is not inferred from this fixture.

WP0 itself remains **NO**.
