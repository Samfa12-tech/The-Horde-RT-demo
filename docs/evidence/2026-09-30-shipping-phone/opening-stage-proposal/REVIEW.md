## Consequential findings

1. **Probe rows lack opening-room and OpaqueFast provenance.** `android_probe_bridge.cpp:178–184` saves only submitted identity and per-stage booleans; `CollectOpeningProbe` at `235–261` prints identity, stage, status and duration, but no zone or active strategy. The submission identity has no strategy/zone field. Thus these records cannot establish that a timing belongs to the opening room or that the selected strategy was `OpaqueFast`, despite the existing state export elsewhere. Save the record-time zone and actual selected strategy with this pending identity and include them in each row before using the output for that comparison.

2. **Aborted/uncollectable measurements disappear without a stage result.** On failed device idle, `CompleteRtEvidenceAfterDeviceIdle` returns before probe collection (`android_probe_bridge.cpp:2152–2160`); later teardown destroys the timers (`2379–2388`) without a probe terminal-status row. Likewise, an invalid submit transaction cancels both recordings without creating pending evidence (`3077–3093`). This avoids unsafe query reads and false durations, but leaves no explicit `idle-failed` / `identity-unavailable` outcome in the probe log. Emit a non-duration status for these paths, without collecting query data or making the frame fail.

## Checked paths and timing semantics

- Successful fence path collects the probe at `android_probe_bridge.cpp:2487–2508`, only after `vkWaitForFences` succeeds. Successful device-idle drains collect every frame slot in `CompleteRtEvidenceAfterDeviceIdle` (`2162–2175`), reached from final benchmark drain, render-failure drain, swapchain release/recreate, scale change, and teardown. Failed idle does not collect.
- After successful `vkQueueSubmit`, the probe stores the exact prevalidated `submitTransaction.identity` and submits each recorded timer using that identity's `submissionSerial` (`3077–3088`). Collection joins on consumed result, matching slot, and matching sequence (`243–246`). Record/command-end/fence-reset/queue-submit failures cancel probe recordings (`2937–2948`, `2982–2986`, `3008–3012`, `3048–3052`). Optional stage failures do not reject rendering.
- The two query pools are initialized after scene setup (`2321–2334`), reset only after a successful device-idle release/scale transition (`2025–2027`, `3290–3292`), and destroyed before device destruction (`2383–2388`). No ownership defect found in these paths under successful operation; a failed-idle teardown intentionally cannot claim samples.
- Stage endpoints use the new `GpuFrameTimer` stage parameters. The AS interval is bracketed with `VK_PIPELINE_STAGE_ACCELERATION_STRUCTURE_BUILD_BIT_KHR` around `UpdateDynamicInstances` (`PresentableTinyRtScene.cpp:5464–5478`); dispatch uses the selected RT-shader or compute stage around only `vkCmdTraceRaysKHR_`/`vkCmdDispatch` (`5558–5580`). `RtExecutionPolicy` currently supplies a single RT or compute stage. This is a timestamp interval at the named pipeline stage, not a standalone GPU-engine counter; the AS-bracketed result does not include host-side geometry preparation. Default timer calls remain TOP_OF_PIPE/BOTTOM_OF_PIPE.

Conclusion: no consequential query-pool/fence/transaction-serial ownership defect found in the successful path. The provenance omission is blocking for the intended OpaqueFast opening-room interpretation; terminal status rows for uncollected/identity-less stages are needed for complete probe accounting. Build and unit-test success do not establish runtime acceptance.
