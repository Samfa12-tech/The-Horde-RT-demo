# OpaqueFast vs GenericDielectric: source-seam review

Read-only comparison of the accepted engineering shader source and the `source-eaf` profile worktree. The profile's only renderer-source override is the investigation-only `genericTransmissionActive_ = true` in `PresentableTinyRtScene.cpp`; the committed raygen GLSL/include content is unchanged between `eafbf82` and current `ca57e55`. The checked-out profile shader text is CRLF while the current engineering copy is LF, so raw file hashes differ despite clean source diffs. The override selects the GenericDielectric pipeline and corresponding push-constant/evidence strategy on the same scene. The two packaged shader modules are intentionally different compiler variants, not identical shaders with only a runtime scene flag.

## Shared primary and opaque-hit path

- `shaders/raytracing/minimal.rgen` includes the same `include/rt_frame.glsl` in both builds. The frame path forms the same primary ray/mask, calls `traceScene(..., 10000.0, primaryMask, 0.002, controls.waterQuality < 0.5, true)`, shades it, and composites `integrateFireEmitters` (`rt_frame.glsl:35-62`).
- `traceScene` uses the same origin, `tMin=max(minimumDistance,0)`, `tMax`, ray mask, candidate filters, committed-hit decode and material sampling (`rt_hit_decode.glsl:376-449,451-520`). Flags are `NoOpaque` when either water or player-near-face filtering is requested, otherwise `Opaque` (`407-410`); the primary call always requests player-near-face filtering. Generic compilation adds dielectric-spawn fields to `HitInfo` (`400-404`), but ordinary opaque primary hits do not invoke dielectric transport.
- `shadePrimary` routes transmission only when the selected Generic variant is compiled and the decoded hit has transmission above threshold plus the transmission material bit (`rt_dielectric_common.glsl:354-365`). Ordinary opaque/emissive hits use `shadeOpaquePrimary` (`278-310`). Thus the bounded dielectric reflection/refraction/interface loops in `rt_dielectric_transport.glsl` and `rt_dielectric_common.glsl` are present only in the Generic module, but their material-specific transport branch is not taken for an opaque hit. This does not mean Generic's opaque shading is otherwise identical.
- Non-Lean opaque shading can issue the existing one-bounce `traceScene` with `tMax=12`, `tMin=0.002`, and mask `0x37` for player reflection or `0x23` otherwise (`rt_dielectric_common.glsl:297-329`). Both variants retain this bounce and the same material sampling/BRDF inputs, but `offsetRayOrigin` differs: OpaqueFast uses the geometric-normal side times `0.004`; Generic uses `advanceDielectricRayOrigin` with scale-aware epsilon (`rt_lighting.glsl:882-893`). That can change secondary origins/intersections and prevents assuming exact pixel equivalence.

## Shadow/direct-light seam that remains active on opaque receivers

- Direct lighting remains real in both variants: opaque shading calls `shadeOpaqueDirect` and `fireEmitterDirectLighting` (`rt_dielectric_common.glsl:303-310`; `rt_lighting.glsl:1227-1255`). The latter computes the same emitter sample, diffuse/specular terms, skips only when both terms are zero, and traces one shadow segment (plus a second when dual visibility is enabled) (`rt_lighting.glsl:1037-1112`). The four-slot ordinary local/sky batch likewise skips non-contributing slots (`1153-1219`). These routines execute for opaque receivers, including the held fire emitter; the strategy does not disable physical torch shadows.
- The traversal behind those calls changes by compiled strategy. OpaqueFast dispatches `sceneShadowTransmittanceMask` to `visibilityMask` (`rt_lighting.glsl:871-880`), which initializes a `NoOpaque` query (`846-850`), filters transparent world water/glass candidates, confirms remaining candidates, and returns binary visibility only after traversal ends (`851-868`).
- Generic dispatches to `boundedShadowTransmittanceMask` (`871-879`, definition `628-844`). It conditionally sets `NoOpaque` only for segments intersecting known transparent-world bounds (`651-655`), inspects candidates/material metadata, confirms opaque blockers, gathers transmissive interfaces, then nearest-orders and integrates thin tint/closed-volume attenuation subject to fixed budgets (`661-731,746-842`). On an all-opaque unobstructed segment, volume/interface integration is empty; the generic candidate/material checks and its query still remain. A committed opaque blocker returns zero (`733-744`). Do not infer dynamic candidate counts, traversal depth, or time from source/SPIR-V site counts.
- For a mathematically fully opaque segment, returned transmission may reduce to the same binary result, but the flag selection, candidate processing, origin offset, and possibly visited surfaces differ. The diagnostic capture's unchanged-pixel subset failed (`max 214`, `fraction >1 = 0.036708`); this profile is not pixel-equivalent or admitted as a Shipping change.

## Narrow measured follow-up hypothesis and physical boundary

The existing forced-strategy comparison measures the cost of the *whole* Generic strategy, not compiler occupancy, pure glass cost, or one isolated shadow query. The smallest separable follow-up worth asking the lead about is a temporary Generic-module shadow-helper comparison restricted to a proven dry, opaque-only opening segment set: keep the selected Generic shader, all direct-light/emitter calls, samples, masks, endpoint distances, receiver material, and shadowed torch contribution unchanged; switch only the shadow traversal helper between bounded transmittance and binary visibility for segments proven unable to meet water/glass or transmissive instances. Admit no such segment until the actual route/capture and scene bounds substantiate that precondition. Any segment that could cross transparent geometry must retain the ordered physical transmittance path. It would remain investigation-only and requires fresh matched builds/captures plus phone timing; it is not a proposed production simplification or a claimed gain.
